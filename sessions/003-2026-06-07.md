## The new mechanic (what a puzzle is now)

A puzzle is a small **code-construction** drill: one base problem, a language-specific
**scaffold** with five `{{stage}}` holes, and 5 rounds. Each round fills one hole
(stages in fixed `STAGE_ORDER`: `state → iterate → transform → update → output`) by
picking one of 4 `Option`s. Picking all the correct fragments composes the scaffold
into `canonicalSolutions` **exactly**.

- `Option` = `{ conceptLabel (button text), fragments: {python, java}, rationale (reveal) }`.
- Top-level additions: `scaffolds.{python,java}`, `canonicalSolutions.{python,java}`,
  `tests: [{input, expected}]`.
- Removed from the old schema: `RoundType`, `timeLimitSeconds`, per-round `explanation`,
  string options. (`Round.type` → `Round.stage`.)

Per the project's distractor-validation rule (memory note), **only the canonical path is
ever executed/compiled** — distractors are allowed to be broken; that's the pedagogy.

## Key design decisions (made this session, since none were recorded)

1. **Two-tier validation.**
   - `scripts/validate-puzzles.mjs` (the `prebuild`/build gate) is **pure Node, no
     runtimes**: shape invariants *plus* **compose-correctness** — rendering each scaffold
     with the 5 correct fragments must equal `canonicalSolutions` byte-for-byte. This keeps
     Vercel's `npm ci && build` portable (no Python/JDK needed in CI).
   - `scripts/test-puzzles.mjs` (new, **not** in the build) is the behavioural gate:
     runs the Python canonical against `tests` (order-insensitive, deep-sorted compare)
     and **compiles** the Java canonical with `javac`. Run locally: `npm run test-puzzles`.
     Supports `--skip-java` / `IIT_SKIP_JAVA` and a `puzzle-00N` filter.
2. **Python executes, Java compiles.** Generic JSON→typed-Java wiring needs a JSON lib
   (banned by supply-chain rules), so Java behaviour is verified by `javac` (syntax/type
   catch), while Python is run against the tests for real behaviour.
3. **Stage mapping for non-scan problems.** `state/iterate/transform/update/output` fits
   accumulate-over-a-loop problems naturally; for binary search the loop is the `while`,
   and for the two nested-loop cases the inner loop went into one fragment:
   - Min Window Substring: the entire left-contraction `while` is the `update` fragment.
   - LIS: switched to the **O(n log n) patience/`tails`** formulation so it's single-loop
     and maps cleanly (and is the nicer answer anyway).

## Gotchas / surprises

1. **`javac` spawned from Node crashes inside the Claude Code tool sandbox**
   (`AssignProcessToJobObject: (87)` — the JVM conflicts with the harness's job object).
   So `npm run test-puzzles` (full, incl. Java) **can't be run through the agent tools**,
   only its `--skip-java` half. It runs **fine in a normal terminal**; the Java canonicals
   were compile-verified by invoking `javac` directly via PowerShell. Python spawns from
   Node are unaffected.
2. **`solve(input)` convention.** The Python canonical defines `solve` taking the test's
   `input` as its single argument. Object-input puzzles (`{nums,target}`, `{s,t}`) unpack
   inside; the unpack line lives in the scaffold (fixed), not a stage.
3. **Compose-check is exact-string.** Every distractor fragment is free-form, but the *correct*
   fragments must render to `canonicalSolutions` to the byte. One mismatch surfaced and was
   fixed (puzzle-006's correct `transform` Java was missing its `char c = s.charAt(right);`
   prefix). The validator prints a rendered-vs-canonical diff on failure.
