## TL;DR

Changed the core loop from **reveal-per-round** to **build blind, then run**:

1. **Deferred feedback** — during the 5 rounds, picks commit with NO correctness reveal. The
   construction panel builds in a **neutral** staged-change look (numbered lines, no `+/-`, no
   green/red). Selections are changeable until you hit "Next". The player reasons about whether
   their picks cohere before learning if they're right.
2. **Run + show tests** — after round 5 you land on a "ready" screen (full neutral solution + a
   **Run solution** button). Clicking it loads **Pyodide** (Python in the browser, WASM) from the
   jsdelivr CDN, executes the constructed solution against the puzzle's test cases, and **only
   then** reveals everything: a **TestResults** panel (input → expected → your output → pass/fail)
   plus the per-round green/red diff + rationale toggles.

**Java mode** keeps deferred feedback + the full diff/rationale reveal but has **no run** (Pyodide
is Python-only) — it shows a "switch to Python to run" note. All 4 phases shipped and committed;
`npm run build` + `typecheck` + `validate-puzzles` (10/10) green throughout. **Got all the way

## Audit findings (the brief's Phase-0 questions, answered)

- **Test-case shape** (`lib/puzzle.ts` `TestCase`, all 10 puzzles): `{ input, expected }`. `input`
  maps **directly to the single `solve` argument**. Multi-arg problems (two-sum/min-window/
  search-rotated) wrap their args in a dict the scaffold destructures internally
  (`nums, target = data["nums"], data["target"]`), so the harness still passes exactly one value.
  `expected` present on every test → all three display fields (input/expected/actual) available.
- **Entry point** — universally **`solve`** in every Python scaffold/canonical. Parsed at runtime
  from `canonicalSolutions.python` via `/def\s+(\w+)\s*\(/` (→ `parseEntryPoint`), so **no
  `entryPoint` schema field was added** — parsing keeps any future single-function puzzle working.
- **Existing Python runner** (`scripts/test-puzzles.mjs`) compares **order-insensitively at every
  level** via `__norm` (recursive deep-sort of lists, sort dict keys, `json.dumps(sort_keys=True)`
  equality) — **unconditionally, for all puzzles**. There is no per-test compare mode. So "mirror
  the Node runner" = **always unordered-deep**; we replicated `__norm` in TS (`norm`/`equalUnordered`
  in `lib/run-python.ts`). **No `compare` schema field added.**
  - *Known limitation (documented, not fixed):* an ordered-output puzzle (e.g. two-sum `[0,1]`)
    would false-pass a reordered result `[1,0]`. The canonical never triggers it, and consistency
    with the already-validated Node runner is what the brief asked for.
- **Plumbing** — `Player` already receives the full `Puzzle` (incl. `tests`) from the server
  component; no new props threaded.
- **No CSP** exists (`next.config.ts` is empty).

**Phase 0 was a no-op** — the schema already supported running. No code change, no commit.

**Phase 2 — Pyodide run harness** (`1fd9d9a`)
- `lib/run-python.ts` (new, client-only):
  - **Pinned Pyodide `v0.29.4`** (latest stable, 2026-05) from
    `https://cdn.jsdelivr.net/pyodide/v0.29.4/full/` (`pyodide.js` + `indexURL`).
  - **Singleton lazy loader**: injects the CDN `<script>` once, `loadPyodide()`, caches the
    promise (cleared on failure so a later run can retry). Subsequent runs reuse the runtime.
  - `parseEntryPoint(python)`, `runSolution(constructedCode, entryPoint, tests)`.
  - Python harness `__run_all` calls the entry fn per test, JSON-serializing the return **inside**
    the try (so an unserializable/throwing call becomes that test's error), catching exceptions via
    `traceback.format_exc()`. Comparison is done **in TS** (`norm`/`equalUnordered`), mirroring the
    Node `__norm`.
  - **Total-failure safety:** everything in `try/catch` — a syntax error in the composed code or a
    Pyodide load failure returns error `TestRunResult`s, never a thrown exception that crashes the UI.
  - **Main-thread** execution with a one-time "Loading Python runtime…" button state (per brief;
    a Web Worker is a deferred follow-up).

## Pyodide: how it loads + that it actually runs

- **Delivery:** lazy-loaded client script + WASM (~10 MB) from `cdn.jsdelivr.net/pyodide/v0.29.4/
  full/`. NOT an npm install. **User confirmed the jsdelivr load** before Phase 2 (plan-mode gate).
- **CSP (future):** none exists today. When one is added it must allow `https://cdn.jsdelivr.net`
  in `script-src` **and** `'wasm-unsafe-eval'` for WASM. Documented in `lib/run-python.ts` context
  and here.
- **Verified in a real browser** (headless Edge, same-origin Node server, page POSTs its result
  back — no banned automation libs): `loadPyodide` available, runtime up in **~960 ms**,
  all-canonical puzzle-001 **passed 4/4**, a crashing wrong pick (`groups = []` → no `.setdefault`)
  produced **4/4 captured errors** with last line `AttributeError: 'list' object has no attribute
  'setdefault'` — **caught, not thrown.** The local-Python pre-check of the same harness +
  comparison agreed exactly.

## Surprises

1. **Phase 0 evaporated again.** Like session 005, the audit found the schema already supported the
   feature: `solve` is universal and parseable, tests already carry input+expected, and the Node
   runner's unconditional deep-sort meant no `compare`/`entryPoint` field was needed. Phase 0 was a
   documentation no-op.
2. **The Node runner's comparison is globally unordered-deep, not per-test.** Mirroring it is the
   right call for canonical-consistency, but it means ordered-output puzzles can false-pass a
   reordered result. Logged as a known limitation rather than diverging from the validated runner.
3. **Headless screenshot couldn't wait for Pyodide.** `--virtual-time-budget` fires the screenshot
   before the real WASM fetch resolves (caught Pyodide mid-"loading…"). The fix that worked:
   serve the test page from a tiny Node HTTP server and have the page **POST its result back** when
   done — same-origin, no banned deps, definitive proof it ran in a browser.
4. **`Results()` is called, not `<Results/>`.** Rendering it as a nested component type would mint
   a new type each render and remount `ReviewDiff`, dropping its rationale-toggle state on a
   language switch. Calling `Results()` inlines the tree so the state survives.
